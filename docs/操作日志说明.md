## 3. 查询接口

### 3.1 分页查询 `GET /api/admin/logs`

权限编码 `log:list`。**权限已在路由层生效**：`OperationLogController#page` 标注 `@RequirePermission("log:list")`，由 B 的 `RequirePermissionAspect` 统一校验——先经 A 的 `CurrentUserProvider` 取身份（匿名/会话失效 401 `请先登录`），再由 B 的 `AuthorizationQueryService` 实时计算授权快照，缺权限码 403 `缺少访问权限: log:list`，有权限 200；由 `OperationLogPermissionTests` 按真实 AOP 覆盖。

查询参数（全部可选，条件之间为 AND，省略表示不筛选）：

| 参数 | 类型 | 默认 | 规则 |
| --- | --- | --- | --- |
| `current` | long | 1 | 页码，必须 ≥ 1；只接受十进制数字 |
| `size` | long | 10 | 每页数量，1～100；只接受十进制数字 |
| `userId` | long | 无 | 操作人 ID 精确匹配，必须 ≥ 1；只接受十进制数字（`0x1` 一律 400）；合法但不存在时返回空分页 |
| `operation` | String | 无 | 去首尾空白后精确匹配；空串视为不筛选；长度不得超过 100（与 `operation VARCHAR(100)` 对齐） |
| `result` | String | 无 | 只接受 `SUCCESS` / `FAILURE` |
| `createdFrom` | LocalDateTime | 无 | 时间起点，**包含**边界；只接受本地时间 `yyyy-MM-dd'T'HH:mm:ss[.SSS]`，如 `2026-11-08T10:00:00`、`2026-11-08T10:00:00.120` |
| `createdTo` | LocalDateTime | 无 | 时间终点，**不包含**边界；格式同 `createdFrom`；与 `createdFrom` 同时提供时必须起始 < 结束 |

排序固定 `created_at DESC, id DESC`；无需在请求中传排序字段。越界页返回 `records=[]`，保留真实 `total`。

参数白名单（契约 8.1）：**两个接口的白名单不同**——分页接口只接受上表 7 个参数；详情接口不接受任何查询参数（`size`、`current`、`token` 等一律视为未声明）。出现任何未声明参数返回 400，提示语 `未知的查询参数：<参数名>`，多个未知参数按字典序用 `、` 连接。`userId`/`current`/`size` 另做十进制格式校验，`0x1` 这类十六进制写法返回 400 `请求参数错误`。白名单在 Controller 内校验。

### 3.2 详情 `GET /api/admin/logs/{id}`

权限编码 `log:read`（`OperationLogController#detail` 标注 `@RequirePermission("log:read")`，由 `RequirePermissionAspect` 统一校验：匿名/会话失效 401、缺权限码 403、有权限 200）。路径参数按契约接受无前导零的正十进制、最多 19 位且不超过 `Long.MAX_VALUE`：`0x1`、`abc`、`007`、`0`、负数、超过 `Long.MAX_VALUE` 一律 400 `请求参数错误`；不存在时 404 `日志不存在`。**详情接口不接受任何查询参数**，出现即 400 `未知的查询参数：<参数名>`。

## 4. 审计切面

### 4.1 使用方式

`@AuditLog` 必须标在**事务边界之内、通过 Spring 代理被调用**的方法上（典型链路：Controller → `@Transactional` Service → 审计方法）。这样进入切面时事务已经开启，成功日志会在 `beforeCommit` 随业务事务写入，业务回滚时一起撤销、写入失败时业务一起回滚。**不要标在 Controller 上**：事务由 Service 开启，Controller 方法执行时事务尚未开始，切面会走"无事务"分支，Service 提交后才写 SUCCESS，写入失败只记 `error`、业务已经生效，违反《接口与协作约定》§3.5。

`operation` 取自 OpenAPI 的 `x-audit-operation`，不得自造名称或翻译（`@RequirePermission` 待 B 交付，示例仅表示最终形态）：

```java
// Controller：只做参数接收与权限，禁止在此加 @AuditLog
@PostMapping("/api/admin/articles/{id}/approve")
@RequirePermission("article:approve")
public ApiResponse<ArticleState> approve(@PathVariable String id, @Valid @RequestBody ReviewDecisionRequest request) {
    return ApiResponse.success(reviewDecisionService.approve(parseId(id), request));
}

// Service：开启业务事务，把"状态流转 + 审核记录写入"整体交给被审计方法
@Transactional
public ArticleState approve(long articleId, ReviewDecisionRequest request) {
    return reviewAuditWriter.apply(articleId, request.version(), request.comment(), ArticleAction.APPROVE);
}

// 事务内被调用的审计方法：独立 bean，经代理调用（不要同类自调用）
// 状态流转必须在切面内部执行：旧版本/非法状态等异常发生在这里，才能记 FAILURE。
@Component
public class ReviewAuditWriter {

    @AuditLog(operation = "article.approve")
    @Transactional(propagation = Propagation.MANDATORY)   // 加入外层事务，不另起事务
    public ArticleState apply(long articleId, int version, String comment, ArticleAction action) {
        ArticleState state = articleWorkflowService.transition(articleId, version, action);
        reviewRecordMapper.insert(...);
        return state;
    }
}
```

语义：进入切面时 `TransactionSynchronizationManager.isSynchronizationActive()` 为真 → 方法正常返回时 `beforeCommit` 用业务事务写 SUCCESS（写入失败会让业务回滚）；事务回滚或方法抛过异常时 `afterCompletion` 用独立新事务记 FAILURE。只有调用方确实没有事务时（如内部工具方法）才走"返回后立即写 SUCCESS、抛出后立即写 FAILURE"。

该接入方式由 `AuditLogTransactionProxyTests` 用真实 Spring `@Transactional` 代理回归：审计写入失败时业务事务回滚、业务副作用撤销；审计写入成功时日志随业务事务提交、不另开新事务；被审计方法内部的状态流转抛异常（如旧版本/非法状态）时业务回滚，并仍以独立事务记下 `FAILURE`。

### 4.2 记录内容

| 字段 | 来源 |
| --- | --- |
| `operation` | 注解 `operation()` |
| `requestUri` | `HttpServletRequest.getRequestURI()`，不含查询参数 |
| `httpMethod` | `HttpServletRequest.getMethod()` |
| `result` | 由"方法是否正常返回 + 事务最终状态"共同判定：无事务时正常返回 `SUCCESS`、抛异常 `FAILURE`；有事务时方法未抛异常则在 `beforeCommit` 随业务事务写 `SUCCESS`（写入失败使业务回滚），事务回滚或方法抛过异常（即使外层捕获后提交）用独立事务写 `FAILURE` |
| `durationMs` | 方法执行耗时（`System.nanoTime()` 差值转毫秒），事务提交等待不计入 |
| `userId` | `CurrentUserProvider.requireCurrentUser().userId()`：只信任 A 的 Bearer 过滤器写入请求属性的已认证身份；无认证上下文或内部调用记 `NULL`；**不接受请求参数中的 `userId`**（伪造参数不影响记录，已有测试覆盖） |

没有请求上下文（非 Web 调用）时 `requestUri`、`httpMethod` 写空串 `""`。

### 4.3 事务语义

| 场景 | 写入时机 | 结果判定 | 写入方式 |
| --- | --- | --- | --- |
| 调用方存在事务（`isSynchronizationActive()` 为真） | 进入方法时只注册**一个**同步器；方法正常返回时在 `beforeCommit` 用**业务事务**写 SUCCESS，事务回滚或方法抛过异常时在 `afterCompletion` 用独立事务写 FAILURE | 成功：方法正常返回且事务提交；失败：事务回滚或方法抛异常（即使外层捕获后提交，也记 FAILURE） | 成功日志随业务事务提交/回滚（写入失败会回滚业务，杜绝"业务生效但审计缺失"）；失败日志用 `writeInNewTransaction`（`REQUIRES_NEW`）独立提交 |
| 方法正常返回，无事务 | 方法返回后立即写 | `SUCCESS` | `write`（单条语句自动提交） |
| 方法抛异常，无事务 | 捕获后写，再原样抛出 | `FAILURE` | `write` |

补充约定：原业务异常原样抛出，由公共异常处理生成响应，审计不吞异常；写日志自身失败只记录 `log.error`，不影响业务结果；切面不做重试。切面内部用 `boolean[] thrown` 记录方法是否抛过异常，`afterCompletion` 中只有 `STATUS_COMMITTED && !thrown[0]` 才判 `SUCCESS`——这样"方法抛异常、外层捕获后提交其他工作"不会被误记成成功。测试用 `TransactionSynchronizationManager.initSynchronization()` 手工搭建同步环境并手动触发 `afterCompletion` 覆盖提交、回滚、异常后提交三个分支，未连接真实数据库事务。

### 4.4 脱敏边界

切面只采集注解给定的操作名和请求元数据，**不采集请求体、查询参数、请求头、密码、Token、认证头**。登录请求不使用通用参数采集切面（`auth.logout` 仅记录元数据）。审计日志表没有请求体字段，需要排查内容时只能依靠业务表与公共异常日志。

## 5. 与查询接口的关系

写接口调用后可在 `GET /api/admin/logs` 中按 `operation`、`userId`、`result`、时间区间检索。审核历史（`cms_review`）和操作日志（`sys_operation_log`）是两份数据：审核历史记录业务意见与轮次，操作日志记录"谁对哪个路径做了什么、成没成功、耗时多少"，两者不互相替代。

## 8. 组员使用说明

1. 写接口需要留痕时，`@AuditLog(operation = "...")` 必须标在**事务边界之内、经 Spring 代理被调用**的方法上（典型做法：`@Transactional` Service 方法调用独立审计 bean 的方法，或审计 bean 方法标 `@Transactional(MANDATORY)` 加入外层事务）。**禁止标在 Controller 上**（事务由 Service 开启，Controller 处切面走无事务分支，业务提交后才写 SUCCESS、失败不回滚）。被审计方法要覆盖状态流转与审核记录写入，这样旧版本/非法状态等异常发生在切面内部，才能记 `FAILURE`。`operation` 必须与 OpenAPI `x-audit-operation` 完全一致，不自行改名、不加前后缀。
2. 只加在产生业务变更的写接口；列表、详情、导出等只读查询不写业务审计日志。
3. 登录请求不使用通用审计切面（密码/Token 不得入库）；退出登录按 OpenAPI 的 `auth.logout` 记录元数据。
4. 不要用 `try/catch` 包住 `@AuditLog` 方法再手动调用 `AuditLogWriter`，切面已处理成功/失败两种结果；手动写入会与切面重复。
5. 成功路径的审计写入失败会**让业务事务一起回滚**（业务不生效、异常向调用方传播），以保证"业务生效必有审计"；失败路径的 `FAILURE` 记录写入失败只记 `error`，不影响响应。若发现日志缺失，先看应用日志中 `写入操作审计日志失败` 的 error。
6. 需要在业务代码里获取操作人时使用 A 的 `CurrentUserProvider.requireCurrentUser()`（已合入 dev）；查询接口权限由 `@RequirePermission` 校验，业务写接口按 OpenAPI `x-permission` 加同名注解；不要临时解析 Token 或读取请求头，也不要从请求参数取 userId。

### 复验记录（2026-11-22 按本节命令实测）

- 在仓库根目录按上述命令执行（密码由 `Read-Host` 输入；复验时用本机临时值代替）：两遍 005 的输出均为“演示分类 1 / 演示标签 2 / 演示文章 5 / 演示审核历史 2 / 演示标签关联 2”，“同名非演示文章（已跳过）”为 0。
- 中文落库校验：`SELECT HEX(title) FROM cms_article ORDER BY id LIMIT 1;` 返回 `E6BC94E7A4BA…`（UTF-8 字节），而不是 `3F3F…`（`?`），确认中文没有按系统代码页损坏。
- 反例：漏掉 `$OutputEncoding` 一行时，管道里的中文会变成 `?`，按标题匹配的守卫随之失效（实测只写入 2 篇文章），因此这一行必须保留。
- 清理：使用代码块最后两条命令——先 `DROP DATABASE enterprise_cms_seedtest;`，再 `$env:MYSQL_PWD = $null`。已实测清理成功（`SHOW DATABASES LIKE 'enterprise_cms_seedtest'` 为空），不会出现按空密码连接导致的 `Access denied`；清理只影响隔离库，不影响 `enterprise_cms`。

### 与仓库外 e2e 脚本的关系

`数据库/005` 只负责准备演示数据；审计 SUCCESS/FAILURE 必须由真实接口调用产生，因此 e2e 脚本（`课程设计/项目指导/scripts/run_e2e_review_log.ps1`，仓库外）仍按“导入种子 → 启动 jar → 真实登录态请求”执行；后续在 dev 上重跑时，环境变量 `SPRING_DATASOURCE_PASSWORD` 与 e2e 登录账号密码由本机提供，不写入仓库。
