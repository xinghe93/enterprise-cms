# 公共异常处理

公共类型位于 `com.xinghe.cms.common.exception`。Controller 正常返回 `ApiResponse<T>`，业务失败时抛出 `BusinessException`，由自动扫描的 `GlobalExceptionHandler` 生成 HTTP 状态及统一响应体。无需在各 Controller 中重复编写 `try/catch`。

## 业务异常用法

```java
import com.xinghe.cms.common.exception.BusinessException;
import com.xinghe.cms.common.response.ResultCode;

// 使用公共默认消息：HTTP 404，message 为“资源不存在”
throw new BusinessException(ResultCode.NOT_FOUND);

// 使用适合展示给用户的业务提示：HTTP 409
throw new BusinessException(ResultCode.CONFLICT, "用户名已存在");
```

上述两行是独立示例，按实际条件选择使用。业务异常继承 `RuntimeException`，可触发 Spring 默认事务回滚规则；写操作仍须由各模块在 Service 中声明事务。不要捕获后吞掉异常。

构造器拒绝 `SUCCESS`、空结果码和空白消息。自定义消息是对外接口的一部分，不能拼接数据库异常、SQL、密码、令牌或请求原文。服务端 500 即使使用了自定义消息，也只对外返回“系统繁忙，请稍后再试”。

响应示例：

```json
{
  "code": 409,
  "message": "用户名已存在",
  "data": null,
  "timestamp": "2026-11-02T07:00:00Z"
}
```

HTTP 状态为 409；`timestamp` 是实际响应创建时的 UTC ISO 8601 时间。

## 参数校验

请求 DTO 使用 Jakarta Validation 注解和明确、安全的校验消息；Controller 参数加 `@Valid`。

```java
public record CreateArticleRequest(
        @jakarta.validation.constraints.NotBlank(message = "标题不能为空") String title) {
}

// Controller 方法参数示例：
// @Valid @RequestBody CreateArticleRequest request
```

DTO/表单校验失败返回 HTTP 400，`message` 为去重、排序后以“；”连接的校验消息。直接声明在 Controller 方法参数上的约束也由 MVC 方法校验处理，例如 `@RequestParam @Min(value = 1, message = "页码必须大于零") int current`。使用 MVC 内建方法校验时，Controller 类无需添加 `@Validated`。

校验消息不要引用被拒绝的值，也不要通过消息插值展示密码、令牌等敏感输入。缺参、类型转换失败（包括表单 DTO 字段绑定失败）、缺失请求体及无法解析的 JSON 均返回通用“请求参数错误”，不回传原始异常详情。Controller 返回值违反约束属于服务端错误，返回 500。

## 异常与 HTTP 状态

| 场景 | HTTP 状态 / code | message |
| --- | --- | --- |
| 业务参数错误 | 400 | 默认提示或安全业务提示 |
| 业务未登录 / 无权限 | 401 / 403 | 默认提示或安全业务提示 |
| 资源不存在 / 业务冲突 | 404 / 409 | 默认提示或安全业务提示 |
| DTO、表单或方法参数校验失败 | 400 | 明确的校验消息 |
| JSON 无法解析、缺参、参数类型错误 | 400 | 请求参数错误 |
| MVC 路由或静态资源不存在 | 404 | 资源不存在 |
| HTTP 方法不支持 | 405 | 请求方法不支持 |
| 响应格式无法满足 Accept | 406 | 无法生成请求所需的响应格式 |
| 上传超过限制 | 413 | 上传内容超过大小限制 |
| 请求 Content-Type 不支持 | 415 | 请求媒体类型不支持 |
| 未预期异常 | 500 | 系统繁忙，请稍后再试 |
| 框架其他服务端异常 | 原 5xx 状态 | 系统繁忙，请稍后再试 |

处理器继承 `ResponseEntityExceptionHandler`，保留 MVC 已确定的状态和响应头，例如 405 的 `Allow`。405、406、413、415 等框架状态直接使用相同数字作为响应 `code`，无需业务模块自行扩展 `ResultCode`。错误响应统一声明为 `application/json`，包含既有四个字段且 `data=null`。

`ResponseStatusException` 的内部 reason 不直接回传；需要对外显示具体业务提示时使用 `BusinessException`。不要把任意 `IllegalArgumentException` 都当成客户端错误：非 MVC 参数绑定导致的未预期异常仍按 500 处理。

## 日志及适用边界

- 未预期异常、MVC 服务端异常和 500 业务异常记录 ERROR 日志及堆栈；可预期的 4xx 业务错误不重复打印堆栈。
- 处理器不主动读取或打印请求体、请求参数和认证头。异常对象本身仍会进入服务端日志，开发者不得把密码或令牌写入异常消息；服务端日志应按内部数据管理。
- 这是 MVC 异常响应能力，不会实施登录或权限校验；鉴权模块仍须独立实现。过滤器和容器错误分派不经过 Controller Advice，后续需要在对应入口复用响应契约。
- 已提交的响应、下载及流式输出不能保证改写为 JSON；框架已提交响应时遵循 Spring MVC 的原处理流程。
- 本次不增加业务接口、数据库变更或依赖。测试中的 `/__test/` Controller 仅由测试配置注册，不进入生产包。

## 验证

在 `backend/` 中执行：

```bash
./mvnw test
./mvnw clean verify
```

`BusinessExceptionTests` 验证构造器约束；`GlobalExceptionHandlerTests` 使用应用实际 MVC/Jackson 配置、测试专用 Controller 和 MockMvc 验证业务状态、参数错误、404/405/406/415、500 脱敏、日志堆栈及成功响应。测试不查询 MySQL 或 Redis。

接入真实业务接口后，在 Apifox 中按以下方式验证（测试专用 `/__test/` 路径不用于 Apifox）：

1. 正常请求：确认 HTTP 200、`code=200` 及原业务数据。
2. 参数校验：把已接入 DTO 的必填字段置空，确认 HTTP 400、明确校验消息和 `data=null`；发送非法 JSON 或错误参数类型，确认通用“请求参数错误”。
3. 业务失败：请求不存在的资源或制造可重复的业务冲突，确认 HTTP 404/409 与 `code` 一致。
4. 鉴权模块接入后：使用未登录或无权限身份请求受保护接口，确认 401/403 且没有数据变更；本处理器本身不产生鉴权判断。
5. 请求方法错误：以不受支持的方法访问真实接口，确认 HTTP 405、统一响应及 `Allow` 头。
6. 对 POST JSON 接口使用 `Content-Type: text/plain`，确认 HTTP 415。
7. 仅在本地测试环境通过受控方式触发系统异常，确认 HTTP 500、通用提示、无内部异常详情，服务端存在堆栈；不要为此暴露线上故障接口。
8. 所有 JSON 错误响应均核对四个顶层字段、`data=null` 和可解析的 UTC 时间戳。
