# Redis 门户缓存

在目标 MySQL 库执行 [005_portal_cache_revision.sql](../database/005_portal_cache_revision.sql)，再配置 `CMS_CONTENT_CACHE_ENABLED=true` 重启后端。默认 `false`，可用来做缓存关闭组的性能对照。开启时后端会在启动阶段检查缓存版本是否已初始化。使用当前 Redis 连接配置，门户缓存键以 `cms:portal-cache:v1:` 开头，会话使用各自原有键。

| 接口 | 缓存内容 | 生存时间 |
| --- | --- | --- |
| `GET /api/portal/articles/{id}` | 已发布且全员可见的文章详情，按文章 ID、内容版本和元数据版本区分 | 5 分钟 |
| `GET /api/portal/categories` | 门户分类筛选树，包含可见文章所属的启用分类及启用祖先 | 10 分钟 |

两个接口仍须通过身份与权限校验。详情在查询 Redis 前先用 MySQL 核对发布状态、逻辑删除、可见范围、文章版本及作者显示名。命中时省去正文、分类和标签详情查询。分类树命中时只查一个版本行，省去加载完整分类和统计可见文章所属分类的查询。

发布或下架会改变分类树版本，分类变更会改变两个版本，标签改名或启停会改变文章详情版本。版本与业务写入在同一 MySQL 事务中提交，回滚保留旧版本，批量操作只更新一次。旧版本的 Redis 值按时过期。Redis 内容读取失败时直接回源 MySQL。单个缓存值最多 256 KiB，按 UTF-8 序列化后的字节数计算。

安装迁移后，开启和关闭缓存读取的实例都会维护共享版本，可以共用同一个 MySQL 库。滚动部署时应先升级所有写入实例，再开启缓存读取。执行绕过服务层的数据导入或 SQL 修改后，重跑 `005` 更新缓存版本。压测库与正常开发库使用独立 Redis 逻辑库。

## Apifox 验证

1. 使用普通员工令牌重复请求某个已发布文章详情和门户分类树，两次响应的 `data` 应一致。可在对应 Redis 库使用 `SCAN` 匹配 `cms:portal-cache:v1:*`，并检查命中的键带有限 TTL。若要区分命中与回源，临时启用 `logging.level.com.xinghe.cms.content.service.PortalContentCache=DEBUG`。
2. 用审核员下架已预热的文章。普通员工再次请求该详情应立即得到 `404`。若这是该分类分支最后一篇可见文章，刷新分类树后相应选项应移除。
3. 将一篇已审核文章发布到门户。再次读取详情与分类树应立刻可见。用有权限的账号修改该分类名或文章所绑定的标签名，再请求应读到新名称。
4. 用旧版本请求下架，预期 `409`，预热的文章和分类树仍可读取。然后以当前版本下架、逻辑删除，再次请求详情应为 `404`。

性能对比时使用相同数据、请求和并发量。分别记录关闭缓存与开启并预热后的平均响应时间、P95 与 SQL 查询数，保留登录和权限查询在两组中。正式 JMeter 报告另行产出。
