# EnterpriseCMS 四人协作开发指南 V1.0

更新日期：2026-11-05。面向 A/B/C/D 四位开发者及各自使用的 AI 工具。

本指南汇总已有开发基线，并补充共享文件的交付归属、环境启动和集成步骤。业务范围、接口签名与事务规则继续沿用已确认契约；本文不增加业务接口或依赖。实际初始化数据、认证鉴权和共享服务仍需由对应成员实现。

### 1.1 事实来源与冲突处理

- 开发行为遵守用户明确指令及 AGENTS.md。需求细则采用已确认的《接口与协作约定》；旧计划书中的讨论方案和历史实施计划不覆盖已确认选择。
- HTTP 字段、required/nullable、长度、路径和响应模型查 OpenAPI；Java 跨模块签名查《跨模块服务接口》；数据库结构查编号 SQL；公共能力的使用方法查对应文档和现有源码。
- 上述依据应相互一致。发现冲突时，记录位置、影响方和建议，等待相关成员确认后同步修改契约与代码；不能通过自行选择一份文档掩盖冲突。
- 文档中写出的接口和 Java 签名不代表代码已存在。先搜索现有实现；不存在时找负责人交付，不复制另一套类型或生成恒放行实现。
- 截至本指南编写，前后端公共骨架已合入本地 dev；业务服务仍未实现。共享 Apifox 在线导入情况需团队核实，不以仓库 OpenAPI 的存在作为已导入证明。

### 1.2 已确认且不得各自重新选择的规则

| 项目 | 开发基线 |
| --- | --- |
| 技术版本 | Java 25、Spring Boot 4.1.1；其他依赖沿用 pom.xml、package.json 和锁文件，不自行升级 |
| 登录态 | 随机不透明 Bearer Token，Redis 会话，固定 7200 秒，无滑动续期和刷新令牌；不改为 JWT |
| 身份与授权 | A 验证身份，B 查询当前有效角色与权限；不信任客户端 userId，也不把登录时权限永久当成有效权限 |
| ID | Java 内部 Long，HTTP 中业务 ID 为十进制字符串；前端不调用 Number(id)，分页计数和 version 仍按模型使用数字 |
| 时间 | 业务 DATETIME(3) 对应 LocalDateTime，统一上海本地时间；响应外层 timestamp 为 UTC |
| 响应 | ApiResponse、PageResult、BusinessException 复用现有代码；HTTP 状态与 code 一致，空集合 []、空数据 null |
| 文章 | C 维护状态与版本更新能力，D 编排审核/发布；管理员也不能自审，每次成功版本化写入只递增一次 |
| 跨模块写入 | 同一应用和数据源，加入外层事务；禁止将文章、审核与标签关联拆成各自提交 |
| 首期范围 | visibility 仅 ALL；不自行增加部门可见、刷新令牌、附件上传或复杂工作流 |

密码哈希算法和输入字节处理尚待 A/B 在实现前共同选型；本指南不代替该决定，也不预先引入加密依赖。

## 3. 共享文件与首批交付负责人

以下按现有业务归属细化文件创建责任。服务接口与实现均由提供方交付，消费者引用已合入的同一份类型。包名前缀统一为 com.xinghe.cms，准确字段与签名以《跨模块服务接口》为准。

| 文件/能力 | 创建与维护方 | 使用方与交付时点 |
| --- | --- | --- |
| common.contract.CurrentUser、security.CurrentUserProvider | A | B/C/D；身份鉴权首批交付 |
| common.contract.AuthorizationSnapshot、RoleRef | B | A/C/D；有效授权与角色分配接入前 |
| permission.service.AuthorizationQueryService、RoleDirectoryService | B | A/C/D；身份鉴权首批交付 |
| security.annotation.RequirePermission 及权限 AOP | B | 全员；业务受保护入口接入前 |
| common.enums.ArticleStatus、ArticleAction | C | D；文章相关代码接入前 |
| common.contract.ArticleSnapshot、ArticleState、TagView | C | D；文章/标签共享服务接入前，TagView 随标签字典归 C |
| content.service.ArticleAccessService、ArticleWorkflowService | C | D；审核、发布及标签替换联调前 |
| review.service.ArticleTagService | D | C；文章创建/保存携带标签联调前 |
| log.annotation.AuditLog 及审计能力 | D | 全员；关键写操作集成验收前 |

只定义契约类型的交付可以先于完整业务实现；不得添加会在生产加载的伪身份、空成功或恒放行 Bean。依赖未齐时可在测试范围使用替身验证本模块，同时推进不依赖它的功能，不能宣称端到端已通过。

C 的文章 CRUD 编排可以调用 D 的标签服务，D 的审核编排可以调用 C 的状态服务。实现时拆分编排服务和底层共享服务，避免让两个综合 Service 互相注入；不能靠复制实现或开启全局循环依赖来接入。

## 4. 统一开发环境与启动

### 4.1 环境清单

| 项目 | 要求 |
| --- | --- |
| JDK | 25，java -version 与 Maven 实际使用的 JDK 均需核对 |
| Maven | 优先 backend/mvnw；Windows 使用 mvnw.cmd |
| MySQL | 8.4，与现有初始化 SQL 和集成测试基线一致 |
| Redis | 使用团队可连接的本机或开发实例；现有仓库未固定服务版本，联调记录实际版本，登录功能依赖它 |
| Node/npm | 推荐 Node 24，按 frontend/.nvmrc；依赖用 npm ci 安装 |
| 时间 | JVM、MySQL 服务端与连接会话采用 Asia/Shanghai 对应的本地时间；UTC timestamp 单独处理 |

先在仓库根目录核对工作区与团队约定的 dev 提交。工作区干净后再更新基线、创建个人模块分支；已有分支继续使用，不重建或重置。分支遵守团队 feature/user、feature/permission、feature/content、feature/review 命名；工具创建的新分支还须遵守该工具的上级命名约束。AI 不自动提交、推送或合并。

```bash
git status --short --branch
git rev-parse HEAD
java -version
```

四人在开发记录/PR 中写明实际基线提交号，避免仅写“最新 dev”。更新本地分支须保留已有工作，禁止用强制覆盖解决同步问题。

### 4.2 数据库与后端

1. 由开发者确认目标 MySQL 实例和专用开发库。首次初始化在 SQL 客户端执行 database/001_init.sql；脚本内有 CREATE DATABASE/USE enterprise_cms，不能仅通过客户端选库将它当成别的测试库脚本运行。
2. 脚本不含演示账号，也不会自动升级已存在的旧表。已有库先核对结构，再应用后续编号迁移；不删除或清空数据库。
3. 在 IDE 运行配置或当前终端配置下列环境变量，值使用本机实际配置。密码不写入 Git，不在命令示例里放真实凭据。

| 环境变量 | 现有默认值/用途 |
| --- | --- |
| SPRING_DATASOURCE_URL | jdbc:mysql://127.0.0.1:3306/enterprise_cms |
| SPRING_DATASOURCE_USERNAME | root；按实际开发账号配置 |
| SPRING_DATASOURCE_PASSWORD | 默认空；本机设置 |
| SPRING_DATA_REDIS_HOST / SPRING_DATA_REDIS_PORT | 127.0.0.1 / 6379 |
| SPRING_DATA_REDIS_USERNAME / SPRING_DATA_REDIS_PASSWORD | 默认空，按实例配置 |
| SPRING_DATA_REDIS_DATABASE | 默认 0；使用团队约定的开发实例/逻辑库 |
| TZ / JAVA_TOOL_OPTIONS | 可分别设置 Asia/Shanghai、-Duser.timezone=Asia/Shanghai；保留已有 JVM 选项 |

MySQL 服务端/连接会话也需核对时间设置，仅设置 JVM 时区不代表数据库已一致。后续 JDBC 连接参数调整须与 A/B/C/D 同步。

在 backend 目录执行：

```bash
./mvnw -v
./mvnw spring-boot:run
```

默认后端端口 8080。当前 application.yaml 使用 spring.sql.init.mode=never，启动不会自动导入建表或演示数据。应用启动成功不代表登录和业务接口已实现；未实现接口不能作为成功验收。

### 4.3 前端与联机

在 frontend 目录执行：

```bash
npm ci
npm run dev
```

默认浏览器地址 http://127.0.0.1:5173，请求前缀 /api，开发代理目标 http://127.0.0.1:8080。默认配置可直接使用；需要连接另一台电脑时，在本机 frontend/.env.local 设置 API_PROXY_TARGET=http://对方局域网IP:8080 并重启 Vite。后端需允许局域网访问并放行对应端口。

前端 .env.local 由 Vite 读取，不会自动给后端配置环境变量。当前会话令牌仅存内存，刷新需重新登录；不要由某个 AI 自行增加本地持久化。业务页面复用 api 实例和公共错误提示，不重复拼接 /api 或重复解包 data。

## 5. 初始化测试数据的交付方案

**当前只有建表脚本；本节是待实施方案，不代表种子脚本或可登录账号已存在。** 各人可先用本模块测试 fixture 开发；完整联调前按下表补齐可重复运行的数据准备能力。

| 数据/能力 | 责任与前置条件 | 验收要求 |
| --- | --- | --- |
| 密码哈希及账号初始化工具 | A 主实现、B 审查算法/输入处理，先共同确定选型 | 与真实登录使用同一实现；密码由本机输入/环境提供，不截断、不输出秘密 |
| 四种角色、53 个 API 权限与角色权限 | B，依据接口清单与 OpenAPI 的权限目录和默认角色基线 | 使用正式编码，元数据与契约一致；PUBLIC/AUTHENTICATED 不入权限表 |
| 测试部门、员工、用户角色 | A，在 B 的角色数据可用后写入 | 至少可区分管理员、编辑、审核员、普通员工；支持验证停用账号与另一位作者的数据范围 |
| 分类、标签和文章基础数据 | C | 准备可编辑及不同生命周期状态的文章；记录所属作者，便于非法状态和版本冲突测试 |
| 审核历史、文章标签及日志 | D，与 C 联合准备 | 正常业务闭环优先调用真实接口产生；特殊边界 fixture 保持外键与状态一致 |

初始化入口、SQL 编号/文件名和执行命令由各负责人在实际交付 PR 中给出，当前不要执行不存在的 002 脚本。新增脚本遵守表的维护归属和外键顺序：部门/角色/权限 → 用户及角色权限 → 用户角色 → 分类/标签 → 文章 → 审核/标签关联/日志。

每份入口说明输入、前置脚本、生成的数据标识和重复运行行为。建议按用户名/角色编码等业务键定位，插入缺失测试数据，遇到已有不同配置时明确报告；不得默认覆盖真实密码、重置权限、清库或关闭外键约束。测试场景中的数据库断言可使用查询结果取得实际 ID，不假定管理员 ID=1。

仓库只保留非敏感模板和构造方式；真实密码、Token、数据库凭据留在本机，账号密码不进入 SQL、截图、日志或 Apifox 导出。四人先用各自开发库，联调库变更通过编号脚本协调，不多人手工改表。

## 6. 开发及联调顺序

| 批次 | 交付内容 | 进入下一步的条件 |
| --- | --- | --- |
| 1：共同基线 | 全员同步同一 dev 提交，检查工程、文档与 SQL；提供方先交付共享类型/接口声明 | 消费者可引用同一全限定类型，应用中不加载假实现 |
| 2：身份与权限 | A 登录/退出/me/身份入口，B 权限查询/注解/AOP/角色目录；A/B 配套初始化数据 | 登录、退出、停用与越权测试实际通过；权限变更对新请求生效 |
| 3：业务并行 | A 用户部门，B 角色权限，C 分类标签及文章基础，D 标签关联和日志能力 | 各模块前后端和三类接口用例通过；C/D 共享服务可集成 |
| 4：内容闭环 | C 创建/编辑/提交与门户，D 审核/发布/下架及历史/日志 | 完整演示与下方集成清单通过 |
| 5：优化交付 | 按设计计划完成缓存、SQL 对比、JMeter 和过程材料 | 有可复现环境、数据规模、测试计划和实测结果 |

批次是依赖顺序；C/D 可在 A/B 开发时推进不依赖认证实现的代码及测试。每完成一个可验证小功能就发起评审并联调，至少保持计划书约定的每周一次集成，不等四人全部完成。

## 7. 验证与合入清单

### 7.1 本模块检查

后端改动在 backend 目录执行 ./mvnw clean verify；真实 MySQL 验证另按《MyBatis-Plus 配置》显式执行 ./mvnw -Dtest=MybatisPlusMysqlIT test 并配置专用测试连接。后者不会由普通构建自动覆盖，运行前阅读其权限与临时表说明。

前端改动在 frontend 目录执行 npm test 和 npm run build，并人工验证本模块页面、刷新/直达路由、表单错误、加载和移动端交互。文档变更检查路径、链接和契约一致性；只改文档无需声称业务测试通过。

将仓库 OpenAPI 导入团队共享 Apifox 项目，核对 57 个接口并记录同步版本/提交；各成员为自己的接口补正常、错误参数、无权限或非法状态三类用例。OpenAPI 导入不等于用例已运行。

### 7.2 集成验收（以下均为待勾选项）

- [ ] A/B：四类角色可登录，成功返回字符串 ID；失败登录无敏感泄露；未登录/失效 Token 返回 401。
- [ ] A/B：退出后旧 Token 不可用；停用用户的旧 Token 在重新启用后仍不可用；角色/权限关联和启停提交后，新请求采用新规则。
- [ ] A/B：员工分页、部门树、角色分配与权限配置可通过页面完成，关联替换失败保留旧数据。
- [ ] C/D：编辑创建带分类/标签的草稿 → 提交 → 他人驳回 → 修改重提 → 他人通过 → 发布 → 普通员工门户检索 → 下架后门户详情返回 404。
- [ ] C/D：普通员工审核返回 403；本人审核（含管理员）返回 403；不能读取/修改权限范围外的草稿。
- [ ] C/D：草稿直接发布、旧 version、重复审核返回 409；文章和审核记录保持一致；批量混合合法/非法项全部回滚。
- [ ] C/D：文章保存与标签替换不重复递增版本；分页标签批量读取，不产生逐条文章查询标签的 N+1。
