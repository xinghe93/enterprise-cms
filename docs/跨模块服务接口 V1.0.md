# EnterpriseCMS 跨模块服务接口 V1.0

本文件与[接口与协作约定](<接口与协作约定 V1.0.md>)及 [OpenAPI](api/enterprise-cms.openapi.json) 同属 V1.0 开发基线。以下是需要实现的 Java 服务契约，不是已存在的源码；本轮没有向业务模块添加接口空壳。所有调用都在同一 Spring Boot 应用、同一数据源中进行，不通过模块间 HTTP 调用。

## 1. 共享值对象与身份

下列不可变值对象统一放在 `com.xinghe.cms.common.contract`，文章枚举放在 `com.xinghe.cms.common.enums`。Java 中 ID 为 Long，HTTP VO 再转成十进制字符串。集合不得为 null，返回空集合而不是 null，不暴露 Mapper 或可修改实体。

```java
public record CurrentUser(Long userId, String username, Long departmentId) {}

public record AuthorizationSnapshot(
        java.util.Set<String> enabledRoleCodes,
        java.util.Set<String> permissionCodes) {}

public record RoleRef(Long id, String roleCode, String roleName) {}

public record ArticleSnapshot(
        Long id, Long authorId, Long categoryId,
        ArticleStatus status, int version,
        java.time.LocalDateTime publishedAt) {}

public record ArticleState(
        Long id, ArticleStatus status, int version,
        java.time.LocalDateTime publishedAt) {}

public record TagView(
        Long id, String tagName, int status,
        java.time.LocalDateTime createdAt,
        java.time.LocalDateTime updatedAt) {}
```

这些是分别放置的顶层类型，代码片段省略包声明和 import。`departmentId/publishedAt` 允许 null；其他标量非空。Set/List/Map 在构造或返回时防御性复制，不允许外部修改同一次请求的授权快照。

`ArticleStatus` 的值严格为 DRAFT、PENDING_REVIEW、APPROVED、REJECTED、PUBLISHED、OFFLINE，按 name 对应 SQL 字符串，不按 ordinal 存储。`version` 初始为 0，不允许超出 Integer 范围。

## 2. A 提供身份入口，B 提供授权快照

| 类型及责任人 | 固定方法 | 行为 |
| --- | --- | --- |
| `security.CurrentUserProvider`，A | `CurrentUser requireCurrentUser()` | 只读取已验证请求身份；无 Token、无效/过期/已撤销 Token、停用用户均抛 UNAUTHORIZED；不从请求 userId 参数构造身份 |
| `permission.service.AuthorizationQueryService`，B | `AuthorizationSnapshot getForUser(Long userId)` | 校验用户存在且启用后，返回有效角色与权限；用户无效按 UNAUTHORIZED，不返回可误认为已认证的空快照 |
| `permission.service.RoleDirectoryService`，B | `List<RoleRef> lockAssignableRoles(List<Long> roleIds)` | 供 A 的用户角色替换调用；空列表返回空列表；ID 不存在 404，任一角色停用 409；按 ID 升序返回并锁定角色行，直到外层事务结束 |

上述包名均以 `com.xinghe.cms.` 开头。A 维护用户/部门/用户角色，B 维护角色/权限/角色权限；跨表只读 JOIN 可以读取正式关系，但写入责任不改变。

授权快照的 `enabledRoleCodes` 只来自启用用户关联的启用角色，`permissionCodes` 还须过滤停用权限。启用且没有权限的角色仍出现在 enabledRoleCodes 中；用户没有有效角色时两者均为空。C/D 判断 ADMIN 全体范围时只能检查该快照，不能检查会话中旧角色或用于管理回显的 User.roles。

权限注解统一为 `security.annotation.RequirePermission`，`value` 是当前 HTTP 操作的准确权限码。A 的身份入口先运行，B 的 AOP 再校验有效权限，业务 Service 再检查数据范围/状态/版本。`PUBLIC/AUTHENTICATED` 是文档标记，不是数据库权限码。

首期每个请求从数据库重新计算有效授权，可以在同一请求中复用快照，不把它永久写入 Token，也不增加跨请求权限缓存。用户/角色/权限启停和关联变更提交后开始鉴权的新请求必须看到新规则；已经进入业务事务的请求按事务完成。Redis/数据库故障返回 500，不能回退为放行。

A 的角色替换先在事务中校验目标用户，再调用 `lockAssignableRoles`，最后全量替换 `sys_user_role`。B 的方法采用 `MANDATORY` 事务语义，按 ID 顺序使用共享行锁保护“启用校验到关联提交”的窗口；A/B 的角色启停在同一库的正常写锁下串行。B 不替 A 写 sys_user_role。

B 的角色权限替换同样在一个事务中锁定目标角色、按 ID 顺序共享锁定待分配权限后校验并替换关联，避免权限启停与关联替换之间出现未约定的校验窗口。空集合不发出 IN 查询；回滚保持原关联，状态更新通过数据库写锁与这些校验串行。

## 3. C 提供文章访问和状态更新

```java
public interface ArticleAccessService {
    ArticleSnapshot requireReadable(Long articleId);
    ArticleSnapshot lockEditable(
            Long articleId, int expectedVersion, ArticleAction action);
}

public interface ArticleWorkflowService {
    ArticleState transition(
            Long articleId, int expectedVersion, ArticleAction action);
}
```

两者位于 `com.xinghe.cms.content.service`，由 C 实现；共享 `ArticleAction` 放在 common.enums，值如下：

| action | 必须的有效权限 | 原状态 → 目标状态 |
| --- | --- | --- |
| SAVE | article:update | DRAFT/REJECTED 保持；OFFLINE → DRAFT |
| DELETE | article:delete | DRAFT/REJECTED/OFFLINE → is_deleted=1 |
| SUBMIT | article:submit | DRAFT/REJECTED/OFFLINE → PENDING_REVIEW |
| APPROVE | article:approve | PENDING_REVIEW → APPROVED |
| REJECT | article:reject | PENDING_REVIEW → REJECTED |
| PUBLISH | article:publish | APPROVED → PUBLISHED |
| OFFLINE | article:offline | PUBLISHED → OFFLINE |
| BIND_TAGS | article:bind-tag | DRAFT/REJECTED 保持；OFFLINE → DRAFT |
| BATCH_PUBLISH | article:publish-batch | APPROVED → PUBLISHED |
| BATCH_OFFLINE | article:offline-batch | PUBLISHED → OFFLINE |

`requireReadable` 读取未删除文章并实施主约定中的数据范围；不存在/已删除返回 404，无读取范围返回 403。调用方先校验当前 HTTP 操作的功能权限，该方法不再额外叠加 article:read：例如历史接口用 review:list 作为功能门槛，再复用同一数据范围。历史查询不会因有 review:list 就获得别人的草稿范围。调用方应在同一只读事务中完成后续历史查询，保持同一数据库快照。

`lockEditable` 仅用于 SAVE/DELETE：要求已存在事务，锁定文章行，校验功能权限、本人/管理员写范围、状态和版本，返回原快照，**不递增版本**。C 的保存/逻辑删除 Service 在自己的 SQL 中同时写内容/删除标记和 version+1，成功只递增一次。调用不支持的 action 属于编程错误，不当作客户端合法操作。

`transition` 用于 SUBMIT、APPROVE、REJECT、PUBLISH、OFFLINE、BIND_TAGS 及两个 BATCH action，采用 `MANDATORY` 事务语义。内部取得当前身份和同一授权快照，锁定文章、检查准确 action 权限、数据范围、预期状态和版本，然后条件更新并递增一次版本。APPROVE/REJECT 对本人文章返回 403，管理员也不例外。批量 action 校验批量权限码，不额外要求单条权限码。

状态更新 SQL 同时约束 id、is_deleted=0、预期 version 和允许原状态；影响行数不为 1 就不能继续按成功处理。版本或状态冲突返回 409。创建 version=0，成功写操作返回新版本；Integer.MAX_VALUE 不再递增，返回 409。PUBLISH/BATCH_PUBLISH 由 C 的更新能力写数据库本地发布时间，其余 action 保留最近发布时间。

## 4. D 提供标签关联与审核编排

```java
public interface ArticleTagService {
    void replaceBindings(Long articleId, java.util.List<Long> tagIds);
    java.util.Map<Long, java.util.List<TagView>> findByArticleIds(
            java.util.List<Long> articleIds);
}
```

类型位于 `com.xinghe.cms.review.service`，由 D 实现；`cms_tag` 字典仍由 C 写入。关联方法可 JOIN 字典做只读校验，不另建或修改标签实体数据。

`replaceBindings` 采用 `MANDATORY` 事务语义，前提是外层 C/D 编排已验证文章权限/状态并持有对应文章行锁。方法本身只校验并替换 `cms_article_tag`，不改变文章 version/status，不重复记录 HTTP 成功审计。最多 100 个唯一 ID；缺失/null/重复/非法 ID 为 400，不存在为 404。新绑定标签及其状态用共享锁校验，按 ID 顺序锁定；新绑定停用标签返回 409，已有绑定的停用标签可保留。先完成全部校验再替换，空列表清空。

批量读取为空时直接返回空 Map，不生成空 IN SQL；返回 Map 必须包含每个请求 articleId 的键，无标签对应空列表，TagView 按 ID 升序。仅用于已通过访问校验的主表结果，不能借此绕过文章读取范围。C 的文章分页后一次批量取得标签，避免每条文章单查。

| 编排入口 | 固定事务顺序 |
| --- | --- |
| C 创建文章 | 外层事务验证分类 → 插入 DRAFT/version=0 → D.replaceBindings → 查询完整 VO；不调用 transition，不额外递增版本 |
| C 保存文章 | 外层事务 C.lockEditable(SAVE) → 校验分类 → 条件更新正文/状态和 version+1 → D.replaceBindings → 查询完整 VO |
| D 独立替换标签 | 外层事务 C.transition(BIND_TAGS) → D.replaceBindings → 返回 id/status/新 version/排序后 tagIds |
| D 通过/驳回 | 外层事务 C.transition(APPROVE/REJECT) → 插入本轮 cms_review；reviewerId 从身份入口取，result 按 action 生成，comment 按请求；任一失败回滚全部 |
| D 发布/下架 | 外层事务 C.transition(PUBLISH/OFFLINE)，返回新 ArticleState；发布不另插入审核通过记录 |
| D 批量发布/下架 | 先校验全部参数/重复 ID，按 ID 升序调用对应 BATCH transition，任何失败整体回滚，成功结果再按请求顺序返回 |

跨成员写操作都加入外层同一事务，不使用 REQUIRES_NEW 拆分文章、审核和关联数据。需要失败审计时，D 在业务事务回滚后另行写 FAILURE，不能吞掉原异常或留下 SUCCESS。

## 5. 日志与接入责任

D 提供 `com.xinghe.cms.log.annotation.AuditLog`，属性 `String operation()`；值采用 OpenAPI `x-audit-operation`。各 HTTP 写入口只标记一次，内部共享服务不再重复记录同一 HTTP 操作。

成功日志随外层事务提交，失败日志在回滚后记录。日志字段仅取现有表，requestUri 只保留路径，不含 query；不采集请求正文、密码、哈希、Token 或认证头。日志查询的 userName 是当前 `sys_user.real_name` 的 JOIN 结果，允许用户为空，不声称提供姓名历史快照。

调用方落实：A 对接身份/用户角色；B 对接有效角色权限及注解；C 对接文章访问/状态/分类字典；D 对接关联/审核/审计。实现时不得改动这套输入、返回语义或事务边界；确需调整时，在相关成员评审中同步更新本文、OpenAPI 和调用方。
