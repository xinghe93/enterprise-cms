# 统一响应格式

所有业务模块在 Controller 中显式返回 `com.xinghe.cms.common.response.ApiResponse<T>`。普通数据、列表和分页数据共用同一个外层结构。

## 响应字段

| 字段 | JSON 类型 | 说明 |
| --- | --- | --- |
| `code` | number | 成功为 `200`，失败使用下表中的公共结果码 |
| `message` | string | 可向用户展示的提示信息 |
| `data` | object、array 或 null | 实际业务数据；没有数据时保留为 `null` |
| `timestamp` | string | 创建响应时的 UTC 时间，使用 ISO 8601 格式 |

成功示例：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "id": 7,
    "title": "示例文章"
  },
  "timestamp": "2026-10-26T09:20:00Z"
}
```

## 公共结果码

| 枚举常量 | code | 默认 message |
| --- | --- | --- |
| `SUCCESS` | 200 | 操作成功 |
| `BAD_REQUEST` | 400 | 请求参数错误 |
| `UNAUTHORIZED` | 401 | 请先登录 |
| `FORBIDDEN` | 403 | 无访问权限 |
| `NOT_FOUND` | 404 | 资源不存在 |
| `CONFLICT` | 409 | 业务状态冲突 |
| `INTERNAL_SERVER_ERROR` | 500 | 系统繁忙，请稍后再试 |

业务失败可以覆盖默认消息，例如使用 `CONFLICT` 和“用户名已存在”。系统内部异常使用通用消息，异常详情记入服务端日志。

`code` 是 JSON 字段，HTTP 状态是 HTTP 协议的一部分。创建失败响应体不会自动修改 HTTP 状态；Controller 应通过 `ResponseEntity` 设置对应状态，后续全局异常处理器也遵循这一约定。

## Controller 用法

有数据的成功响应：

```java
return ApiResponse.success(data);
```

没有数据的成功响应：

```java
return ApiResponse.success();
```

失败响应：

```java
return ResponseEntity.status(HttpStatus.NOT_FOUND)
        .body(ApiResponse.error(ResultCode.NOT_FOUND));
```

具体业务提示：

```java
return ResponseEntity.status(HttpStatus.CONFLICT)
        .body(ApiResponse.error(ResultCode.CONFLICT, "用户名已存在"));
```

这里的 `ApiResponse`、`ResultCode` 来自 `com.xinghe.cms.common.response`；`ResponseEntity`、`HttpStatus` 来自 `org.springframework.http`。

## 分页约定

分页数据放在 `data` 中，通过 `PageResult.from(page)` 转换 MyBatis-Plus 的 `IPage<T>`；T 使用接口对外的 VO 类型。

```java
return ApiResponse.success(PageResult.from(page));
```

| 字段 | 说明 |
| --- | --- |
| `records` | 当前页记录，空页为 `[]` |
| `total` | 满足查询条件的记录总数，不是当前页条数或总页数 |
| `current` | 当前页码，从 1 开始 |
| `size` | 每页数量，大于 0 |

空页示例：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "records": [],
    "total": 0,
    "current": 1,
    "size": 10
  },
  "timestamp": "2026-10-26T09:20:00Z"
}
```

## 验证

在 `backend/` 目录执行 `./mvnw test`，现有契约测试会通过应用实际的 Jackson 配置检查成功、失败、空数据和分页 JSON，测试不查询 MySQL 或 Redis。

业务接口接入后，在 Apifox 中验证：

1. 正常请求：检查 HTTP 200、四个顶层字段、`code=200` 和实际业务数据。
2. 无返回数据的成功操作：检查 `data` 存在且值为 `null`。
3. 分页请求：检查 `data` 只包含上述四个分页字段，空查询结果的 `records=[]`。
4. 失败请求：检查对应的 HTTP 4xx/5xx、失败 `code`、业务消息和 `data=null`。
5. 检查 `timestamp` 是可解析且以 `Z` 结尾的 UTC ISO 8601 时间。

本次提供公共响应类型，没有新增业务接口或全局异常处理器；Spring Boot 默认错误响应、下载与流式响应不由这些公共类型自动改写。
