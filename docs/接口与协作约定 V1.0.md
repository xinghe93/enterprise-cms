- [OpenAPI 3.0.3 JSON](api/enterprise-cms.openapi.json)：57 个接口、96 个数据模型，全部对齐参数、响应、权限和业务边界，供 Apifox 导入和契约检查。
- [接口、权限及默认角色清单](api/接口清单.md)：A/B/C/D 归属、HTTP 方法、路径、权限编码和默认授予角色。
- [跨模块服务接口](<跨模块服务接口 V1.0.md>)：固定身份/有效授权快照、文章状态、标签关联的 Java 值对象、方法签名与事务责任。
- 既有依据：[设计计划书](<EnterpriseCMS 项目设计计划书 V1.0.md>)、`database/001_init.sql`、[统一响应](统一响应格式.md)、[公共异常处理](公共异常处理.md)、[MyBatis-Plus 配置](<MyBatis-Plus 公共配置.md>)。

若约定与已有实现或 SQL 冲突，先提出调整方案，不直接修改其他成员模块。共享 Apifox 项目应导入当前版本，仓库保留同版本 OpenAPI；变更需同步更新二者并由受影响的成员评审。当前只更新了仓库文件，尚未在线同步 Apifox。

## 1. 已有约束：本轮继续沿用

| 项目 | 既有规则 |
| --- | --- |
| API 前缀 | `/api/auth`、`/api/admin`、`/api/portal` |
| 统一响应 | `code`、`message`、`data`、`timestamp`；空数据必须为 `null` |
| HTTP 状态 | HTTP 与响应 `code` 一致；成功 200，参数 400、未登录 401、无权限 403、不存在 404、业务冲突 409、系统错误 500 |
| 框架请求错误 | 保留 405/406/415 等状态，405 保留 `Allow`；通过现有 Advice 返回统一 JSON |
| 分页 | `current` 默认 1、`size` 默认 10，范围 1～100；响应 `records/total/current/size`，越界页为空，保留真实总数 |
| 权限 | 后端必须验证身份、有效权限和数据范围；前端菜单不构成鉴权 |
| 文章可见范围 | 首期仅 `ALL`；门户仅展示未删除且已发布文章，不扩展部门级可见范围 |
| 数据访问 | 单表 MP，多表明确 SQL/XML；列表 JOIN 或分页后批量查询，避免 N+1 |
| 数据库 | 沿用 12 表；自增主键、复合关联键、文章逻辑删除及版本字段不改 |
| 历史 | 审核记录每轮新增，不覆盖；停用账号不删除历史文章或审计日志 |

空结果集合为 `[]`。所有新增写入、状态变更均返回 HTTP 200；有结果时返回明确 VO，没有结果时 `data=null`，不使用 204。

本约定使用单一页码/数量入口，不接受客户端直接提交 MP `Page` 或任意排序 SQL。各列表默认排序在 OpenAPI 的接口说明中明确，并用 ID 作为排序兜底。

## 2. 已确认的核心选择

用户已确认采用下表方案，后续开发直接沿用，无需重复确认。全部 57 个接口的具体边界也已按该方案提前对齐。OpenAPI 版本为 `1.0.0`，根和所有操作的 `x-contract-status=aligned`；全部 `x-implementation-status=not-implemented`。优先级字段只表示开发顺序，不表示还有接口未对齐。

| 编号 | 已确认方案 | 负责接入方 |
| --- | --- | --- |
| D1 登录态 | 使用随机不透明 Bearer Token，Redis 保存会话；默认有效期 7200 秒，本阶段不增加刷新令牌。密码哈希算法及输入字节处理由 A/B 在实现中选型，满足当前请求约束后再生成账号数据 | A、B |
| D2 ID 和时间 | JSON 中业务 ID 统一为十进制字符串，Java 内部仍为 Long；业务 DATETIME 使用毫秒精度本地时间，部署会话约定 Asia/Shanghai，外层 `timestamp` 继续 UTC | 全员与前端 |
| D3 初始权限与数据范围 | 使用 EMPLOYEE/EDITOR/REVIEWER/ADMIN 四个初始角色编码，功能权限按接口清单、数据范围按第 3.2 节矩阵；编辑可管理分类/标签，审核员可审核/发布/下架。所有人（含管理员）禁止审核本人文章。门户及分类/标签筛选入口由 C 负责 | 全员 |
| D4 内容流转 | 仅草稿/驳回/下架内容可编辑、删除及替换标签；下架内容修改后回草稿，下架后再次发布须重新审核；文章写操作都带版本号 | C、D |
| D5 集合与删除 | 批量发布/下架最多 100 条，全成全败；角色/权限/标签集合采用全量替换，空集合清空；分类只要仍有任何文章外键引用（含逻辑删除文章）就不能物理删除 | 相关责任人 |

D1 已确定为 Redis 不透明 Token。后续如需变更登录态方案，须同步评审退出、账号停用和权限变更行为；本轮不添加会话实现、加密依赖或密钥配置。

D2 的字符串 ID 用于避免前端将长整型 ID 当作 JavaScript Number 时丢失精度。该选择需要落实到 DTO/VO，当前 `ApiResponse` 不会自动转换 Long；不能据 OpenAPI 认为全局序列化已经配置。ID 必须是正整数且不超过 `9223372036854775807`；OpenAPI 的字符串模式只验证外形，Long 上界须在服务端验证。`parentId/departmentId` 允许 `null`，根节点不使用虚构的 `"0"`。

业务时间示例为 `2026-11-02T16:00:00.000`，没有时区偏移；`timestamp` 示例为 `2026-11-02T08:00:00Z`。二者不得互相当成同一种时间类型。筛选起止时间采用左闭右开区间，起始必须早于结束。

## 3. 模块归属与跨模块调用

### 3.1 A ↔ B：身份、用户角色和权限

| 能力 | 负责方 | 协作边界 |
| --- | --- | --- |
| 登录、退出、`/auth/me` | A | A 验证密码和账号状态、创建/撤销会话，并提供当前身份入口 |
| `sys_user_role` 与用户角色替换 | A | A 校验用户；角色有效性通过 B 的查询能力校验；A 写关联，B 不重复维护第二份关系 |
| 角色、权限、角色权限关联 | B | B 校验角色/权限状态，提供用户当前有效权限计算能力 |
| `/auth/permissions`、权限注解及 AOP | B | 从当前身份拿 userId，读取启用的角色和权限；不能接受请求传入的身份代替当前用户 |
| 当前身份公共入口 | A 提供、B 接入 | `CurrentUserProvider.requireCurrentUser()` 返回 userId/账号/部门等最小身份信息，缺少有效登录态抛出 UNAUTHORIZED |

具体包名、签名和只读 DTO 已在[共享服务契约](<跨模块服务接口 V1.0.md>)固定，尚未在仓库中实现。B 的 `AuthorizationQueryService.getForUser(userId)` 返回 `AuthorizationSnapshot(enabledRoleCodes, permissionCodes)`，两者都只含当前有效项。停用 ADMIN 不能因旧 Token 或管理回显而继续扩大数据范围。修改服务签名时须同步调用方和契约。

登录请求和响应字段：

```json
{
  "username": "editor_demo",
  "password": "由测试环境提供，不使用仓库内固定密码"
}
```

成功数据包含 `accessToken`、`tokenType="Bearer"`、`expiresIn` 和 `user`；Token 示例仅占位，不是凭据。登录失败统一 401 及“用户名或密码错误”，不区分账号不存在、密码错误或停用状态。

受保护请求使用 `Authorization: Bearer <token>`。除登录外，当前身份接口也必须登录；它们不额外要求某个权限项。退出撤销当前 Token；后续旧 Token 请求返回 401。账号停用后旧会话不可继续使用。用户角色、角色状态、角色权限或权限项状态变更后，有效权限必须及时更新；不能只信任登录瞬间的权限快照。

每次成功登录创建独立 Token，不踢出其他登录。有效期从签发起固定 7200 秒，普通请求不滑动续期；退出只撤销当前会话，重复使用该 Token 退出返回 401。停用账号使所有旧会话失效；重新启用也不恢复旧 Token，必须重新登录。账号状态与会话签发须协调，禁止按旧的启用快照建立可用会话。依赖故障不能伪装成登录成功。

A 的用户角色替换、B 的角色权限替换均在各自 Service 的单个事务中完成：先校验所有 ID 和状态，再替换关联，任一失败整体回滚。权限变更在数据库提交后生效；若使用权限缓存/会话失效通知，应在事务提交后清理或刷新，回滚时保留原权限。不得先刷新缓存再提交数据库。账号停用和角色/权限启停同样需要处理提交后的会话或权限失效。

首期不引入跨请求的权限缓存；B 每个请求查询有效授权，可在同一请求中复用。变更提交后开始鉴权的新请求必须使用新规则，已进入业务事务的请求按事务完成。管理 User.roles 返回全部已分配角色（含停用）及每项 status；角色权限管理查询同样返回全部已分配权限。它们按关联 ID 升序，用于界面回显，绝不能代替授权快照。

员工创建不接受角色字段，角色分配通过单独接口进行。用户响应永远不包含 password/passwordHash。用户名及部门/角色/权限编码创建后不可修改；员工资料接口修改姓名和部门，账号启停使用独立状态接口。密码重置不在首批接口中，A 后续如需增加应单独评审。

### 3.2 A ↔ C：文章作者和组织

文章创建时作者取当前身份，客户端不能传 `authorId` 冒充作者。C 可通过正式外键 JOIN `sys_user`、`sys_department` 查询作者和部门；不另建员工副本，也不为文章列表逐条调用用户查询。需要服务调用时由 A 提供批量用户摘要接口。

后台按作者过滤只是查询条件，不能扩大请求者的数据权限。首期按已确认的 D3 采用以下数据范围，不引入部门范围或新的数据权限表。

| 身份/能力 | 后台列表与详情 | 编辑/删除/绑定标签/提交 | 审核/发布/下架 |
| --- | --- | --- | --- |
| 普通员工 | 不具备后台文章功能权限，拒绝访问 | 无权限 | 无权限 |
| 内容编辑 | 本人未删除文章，所有状态 | 仅本人，且符合第 4 节允许的状态 | 仅另行获得对应权限时可操作 |
| 审核人员 | 全体未删除且非 DRAFT 的文章，以及本人 DRAFT | 仅另行获得写权限后按本人范围操作 | 全体文章中符合目标操作状态的记录；审核不得是本人文章 |
| 管理员 | 全体未删除文章，包含 DRAFT | 全体文章，但仍受状态、版本和具体 API 权限限制 | 全体文章且符合状态；同样禁止自审 |
| 门户访问 | 所有角色均只看未删除、PUBLISHED、ALL | 不提供门户写接口 | 不提供门户审核接口 |

多角色的读取/管理范围取并集，但必须先具有该 API 的有效功能权限。管理员的全体范围不等于绕过权限注解。自定义角色默认是本人范围；若获得任一审核/发布/下架能力（含待审核列表或批量发布/下架权限），读取范围采用审核人员规则，仍须具备文章列表/详情权限。自定义角色的审核/发布操作采用对应状态范围；编辑类写操作仍仅本人，除非同时具有管理员角色。不能仅凭 `review:list` 历史查询权限扩大文章读取范围。

所有范围在 Service/SQL 中实施：列表先应用数据范围再分页计数，详情及写入分别检查目标记录；不能先查询全量分页再在 Java 中过滤。`authorId` 查询参数只能缩小范围。审核历史查询继承目标文章当前的读取范围，不能通过历史接口读取不可见草稿。

为支持门户分类/标签检索，接口规划包含 `GET /api/portal/categories` 和 `GET /api/portal/tags`，由 C 提供只读筛选选项，四类初始角色均获得对应门户权限，不能借用需要后台权限的管理接口。职责及权限按 D3 执行，这两个接口的实现仍在后续批次。

门户分类树只显示启用且本身/后代拥有可读已发布文章的分类，并补齐启用祖先；停用祖先下的分支不作为筛选选项。分类筛选 `categoryId` 包含该节点及后代。门户标签分页只显示启用且关联至少一篇可读已发布文章的标签，按标签 ID 去重计数。没有已发布文章的选项不展示，整个库没有可读文章时分类返回 `[]`、标签返回空分页。筛选目录不改变文章本身的可读条件，停用目录项的历史文章仍按其发布状态处理。

### 3.3 C ↔ D：文章、审核和标签关联

| 内容 | 归属 | 调用规则 |
| --- | --- | --- |
| `cms_article`、分类、标签字典 | C | C 定义文章状态和版本条件更新能力；D 不自行创建第二套文章实体/枚举 |
| 草稿保存与提交审核 | C | C 编排事务；创建/保存携带的 tagIds 委托 D 的关联服务写入 |
| 审核/发布/下架及审核历史 | D | D 的 Service 开启事务，调用 C 的文章状态变更能力，并新增审核记录 |
| `cms_article_tag` | D | D 提供全量替换关联的内部能力；C 不直接写关联 Mapper |
| 文章与审核/标签的联合查询 | 查询接口负责人 | 使用正式关系 JOIN 或批量查询，读关联不改变表的维护归属 |

C 提供 `ArticleAccessService` 和 `ArticleWorkflowService`，分别负责可读/可编辑快照与状态变更，具体签名和 action 在共享服务契约中列出。按“ID + 预期状态 + version + is_deleted=0”条件变更文章；成功递增一次 version，影响行数为 0 时区分不存在/冲突，不得继续写审核记录。

D 提供 `ArticleTagService.replaceBindings(articleId, tagIds)` 和批量读取能力。内部方法采用 MANDATORY 事务语义，只替换关联，不再次递增文章版本；外层 C/D 编排服务负责一次内容变更的校验、行锁与版本更新，避免保存文章时递增两次。

`POST /articles` 和 `PUT /articles/{id}` 的 tagIds 由 C 接收，D 实施写入；`PUT /articles/{id}/tags` 的 HTTP 入口归 D，由 D 校验数据权限、调用 C 的版本/状态能力后替换绑定。跨模块调用加入同一个 Spring 事务，不使用 `REQUIRES_NEW` 拆开文章与关联写入。任一失败整体回滚。

角色、权限和标签集合最多 100 个且不得重复；不存在 ID 返回 404。角色/权限全量替换中的每个请求项都必须启用，否则返回 409；既有停用项应在下一次全量替换时移除，停用本身不删除历史关联且不参与有效权限。标签仅新增绑定项必须启用，已绑定的停用标签可明确保留或清除。空列表表示清空，不代表“不修改”。草稿创建省略 tagIds 等同空列表；文章完整保存必须明确提供 tagIds。

### 3.4 B ↔ 全员：权限编码

B 提供 `@RequirePermission("article:submit")`，放在受保护 Controller 的具体操作入口。注解类、AOP、当前身份接入和失败响应均由 B 实现后再供全员使用；本轮不添加空实现或恒放行实现。API 权限项的 path/method 是元数据，鉴权以编码注解为准，不再根据可编辑元数据另建一套放行规则。

OpenAPI 的每个受保护业务操作有唯一 API 权限编码，`x-permission-catalog` 同时提供路径和方法，可映射到 `sys_permission` 的 API 权限项。当前基线共 53 个编码，默认角色分配按 D3 执行，尚未写入数据库；接口变更时同步评审对应权限。登录标记为 PUBLIC，当前身份/权限/退出标记为 AUTHENTICATED，这两个标记不是权限表记录。

每个操作先验登录，再验功能权限，最后验数据范围、状态及版本。后台不允许的数据访问返回 403；门户对于未发布、已删除或不存在的文章统一 404。管理员角色显式分配全部 API 编码，不依赖硬编码超级管理员绕过校验。

MENU/BUTTON 权限和前端路由由 B 与前端骨架阶段共同补齐。本轮给出 API 权限清单，不臆造尚未存在的前端页面路径。

### 3.5 D ↔ 全员：操作日志

D 提供 `@AuditLog(operation="article.submit")` 和审计切面；各接口的操作名已记录为 OpenAPI `x-audit-operation`。记录现有表字段：userId、operation、requestUri、httpMethod、result、durationMs、createdAt。`requestUri` 仅保存路径，不带查询参数；不新增请求体字段。

记录用户/部门/角色/权限变更、文章创建/保存/删除/提交/审核/发布/下架和标签关联操作。正常只读查询不强制写业务审计日志。登录请求不使用通用参数采集切面；账号密码、Token、认证头、正文和完整请求参数都不得写入日志。

成功业务日志随业务事务提交，事务回滚不得留下 SUCCESS。已授权但执行失败的操作可由 D 在业务回滚后单独记录 FAILURE；记录机制不能把原业务异常吞掉，也不能将失败操作伪装成成功。系统异常堆栈仍由现有公共异常处理负责。日志列表/详情返回表字段及 JOIN 得到的当前操作人显示名称，不返回不存在于表中的历史姓名快照或请求载荷。

## 4. 文章状态、版本与批量操作约定

| 操作 | 原状态 | 结果状态 | 负责方 |
| --- | --- | --- | --- |
| 创建草稿 | 无 | DRAFT | C |
| 保存/替换标签 | DRAFT、REJECTED | 保持原状态 | C / D |
| 修改下架内容/替换标签 | OFFLINE | DRAFT | C / D |
| 提交审核 | DRAFT、REJECTED、OFFLINE | PENDING_REVIEW | C |
| 通过 | PENDING_REVIEW | APPROVED | D |
| 驳回 | PENDING_REVIEW | REJECTED | D |
| 发布 | APPROVED | PUBLISHED | D |
| 下架 | PUBLISHED | OFFLINE | D |
| 逻辑删除 | DRAFT、REJECTED、OFFLINE | is_deleted=1 | C |

已有设计明确的主链继续沿用；编辑/删除范围、自审限制及 OFFLINE 的细则按已确认的 D3/D4 执行。待审核、审核通过和已发布内容不能直接改正文或标签；先走允许的状态转换，避免绕过已有审核结论。驳回意见必填，通过意见可为空；每次审核新增一条记录。

版本示例：

```http
POST /api/admin/articles/123/submit
Content-Type: application/json
Authorization: Bearer <token>

{"version": 2}
```

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {"id": "123", "status": "PENDING_REVIEW", "version": 3, "publishedAt": null},
  "timestamp": "2026-11-02T08:00:00Z"
}
```

再次以 version=2 提交返回 409；接口不得再插入审核记录或重复发布。文章逻辑删除通过 query 参数携带 version，其他写操作使用 JSON 中的 version。创建由服务端置 0，发布时间由发布流程生成，客户端不传状态、作者、删除标记和发布时间。版本达到 Integer.MAX_VALUE 后不得溢出，写操作应返回冲突，由维护流程处理。

批量发布/下架请求为 `{"items":[{"id":"123","version":3}]}`，1～100 条，ID 重复返回 400。D 在一个事务中校验权限、每项状态和版本，按稳定 ID 顺序处理锁竞争；任一项失败整体回滚，无部分成功结果。成功时返回与输入顺序一致的文章状态数组。401/403/404/409 分别表达身份、权限、资源或状态/版本问题。

## 5. 删除、停用与外键边界

- 分类创建时省略 parentId 表示根节点，省略 sortOrder 表示 0；分类更新采用完整 PUT，parentId（可为 null）、categoryName、sortOrder 都必填，省略字段返回 400，不隐式重置或保留旧值。
- 员工、角色和权限首批采用启停，不提供物理删除接口，保留历史及关联。
- 部门存在子部门或任何员工引用时禁止物理删除，包括停用员工；树节点不允许成为自身或后代的父节点。
- 分类存在子分类或任何文章引用时返回 409，**包括逻辑删除文章**。现有外键没有因逻辑删除自动解除引用，不能只检查正常文章就声称可删除。分类树同样禁止将节点移动到自身或其后代下。
- 标签存在 `cms_article_tag` 关联时返回 409，C 不暗中删除 D 维护的关联。停用标签保留历史绑定，禁止新增绑定；已有绑定的保留/清除应由显式文章保存操作表达。
- 分类/标签停用后不允许作为新文章或新绑定的选择；保留已有文章的历史分类/标签信息，门户文章是否可见仍由文章状态、删除标记和 visibility 决定。若希望停用分类同时隐藏全部文章，须由 C/D 评审变更并同步缓存规则。

原文章分类未变时，可保留已停用的分类或祖先；新建文章或切换分类时，目标及所有祖先必须启用。新选员工部门、部门/分类父节点同样检查祖先链；原引用不变可保留停用引用，null 表示清除部门或移动到根。引用不存在返回 404，新增停用引用返回 409。部门/分类启停只修改当前节点，不级联子节点、员工账号或文章发布状态；员工登录只受账号本身的启停状态影响。

本约定沿用当前外键，不增加级联删除，本轮没有执行删除 SQL。若需要变更为可删除被逻辑删除文章引用的分类，应单独评审历史展示及数据库迁移方案。

## 6. Apifox 导入与首批验证

Apifox 官方支持导入 OpenAPI 3.0 JSON。已有项目可在“项目设置 → 导入数据”选择 OpenAPI/Swagger，导入 `docs/api/enterprise-cms.openapi.json`，检查分组、请求/响应模型及 57 个接口。操作依据：[官方导入说明](https://docs.apifox.com/doc-5174534)。

导入后配置实际 `baseUrl` 和本机测试账号，按各角色保存 Token 环境变量；不要导出真实密码或 Token 到 Git。权限与负责人扩展字段保留在原 OpenAPI，若可视化界面不显示，应以接口清单对照。文件生成和结构校验不代表已连接团队 Apifox 项目，也不代表业务接口可调用。

四人各自至少提供以下三类用例：

| 类型 | 代表用例 | 核对项 |
| --- | --- | --- |
| 正常路径 | A 新建员工及分配角色；B 分配权限；C 保存草稿；D 审核/发布 | HTTP 200、统一四字段、ID 类型、持久化结果 |
| 错误参数 | 空标题、非法 JSON、size=101、重复关联 ID、缺失 version | HTTP 400、清晰提示、data=null，无部分写入 |
| 无权限/非法状态 | 普通员工审核、编辑改别人草稿、直接发布草稿、旧版本更新、重复审核 | 401/403/409 正确区分，内容与审核历史不发生越权变更 |

另外验证：门户按 ID 访问草稿返回 404；停用账号的旧 Token 不可用；角色权限变更后再次请求生效；批量混合合法/非法项全部回滚；删除被逻辑删除文章引用的分类按确认后的规则处理；审计日志包含操作结果但没有密码/令牌。

OpenAPI 描述的是契约，不包含 Apifox 自动化测试场景、数据库断言或性能报告；这些在成员完成接口后补齐。普通文档结构检查也不能代替真正的登录、鉴权和事务测试。

## 7. 全量对齐与开发顺序

全部 57 个接口均已对齐并可作为开发基线，OpenAPI 操作状态统一为 aligned。以下 4 个接口的 `x-implementation-priority=1`，表示优先实现公共登录鉴权；其余接口为优先级 2，各成员可以同步开发自己的功能，不需要再等一轮接口确认。

| 方法与路径 | 负责人 | 首批交付 |
| --- | --- | --- |
| `POST /api/auth/login` | A | 账号密码校验、账号状态校验、Redis Token、默认 TTL 7200 秒 |
| `POST /api/auth/logout` | A | 撤销当前会话，旧 Token 随后访问返回 401 |
| `GET /api/auth/me` | A | 返回当前用户资料，不暴露密码哈希 |
| `GET /api/auth/permissions` | B | 当前启用用户、启用角色、启用权限关联的有效编码集合 |

首批同时落实共享身份入口与后端权限注解/AOP。权限注解通过测试专用受保护接口验证，测试入口不进入生产包。测试账号及权限数据使用可复现脚本或测试 fixture，不在源码中保存固定真实凭据。密码哈希实现需满足现有输入约束，不得静默截断密码。

首批验收至少覆盖：成功/失败登录、停用账号、未登录/失效 Token、退出后旧 Token、无权限拒绝、角色/权限启停及关联变更后生效；检查统一响应和敏感信息处理。数据源与 Redis 故障不能伪装成鉴权成功。

其余 53 个接口的参数、响应、查询、权限和状态规则已同样明确，按各成员代码开发验证。C/D 可同步开发分类、标签、日志查询等功能，并按共享服务固定签名接入文章闭环；确需改约定时走变更评审，不由各人临时各定一套。

PR 中同步说明接口/SQL 变化和测试结果，受影响成员审查，并同步共享 Apifox 与仓库 OpenAPI。前端骨架、环境 README 和演示数据属于后续独立准备任务，本分支没有实施这些功能。

## 8. 全量接口的输入、查询和返回细则

### 8.1 写入字段、默认值与幂等

以 OpenAPI 的 required、nullable、枚举和长度为准。缺失必填、非 nullable 字段传 null、未知 JSON 字段、未知查询参数、非法 ID/枚举/数字/时间返回 400。不能因 DTO 绑定忽略未知字段而允许客户端试图覆盖作者或文章状态。类型及原始长度先按模型校验，再对普通名称/编码去首尾空白并验证非空；枚举严格匹配，密码和正文不 trim。正文必须含非空白字符。

| 模型/操作 | 创建缺省与完整更新 |
| --- | --- |
| 员工 | 创建默认 status=1、roles=[]，省略 departmentId 为 null；更新 realName/departmentId 均必填，null 清除部门 |
| 部门/分类 | 创建默认 status=1、parentId=null、sortOrder=0；更新 parentId/名称/sortOrder 均必填；编码不修改 |
| 角色 | 创建默认 status=1、权限集合为空；更新仅改角色名称 |
| 权限 | 创建默认 status=1；更新 name/path/method 都必填，编码和 permissionType 不修改 |
| 标签 | 创建默认 status=1；更新只改名称 |
| 文章 | 创建 DRAFT/version=0/publishedAt=null，省略 summary 为 null、tagIds 为[]；完整保存须明确 summary（可null）和 tagIds |
| 审核 | 通过时 comment 省略/null 为 null，空白意见归一为 null；驳回 comment 非空白且必填；均携带 version |

API 权限类型在创建和修改时遵守同一规则：API 的 path 为三个 API 前缀下的不含 query、fragment 或空白的路径，可含 `{id}`，method 是声明的大写方法；MENU/BUTTON 的 method 必须 null。修改时根据数据库中已有 permissionType 校验，不允许请求改变类型。

状态接口重复设置同一状态、角色/权限全量替换相同有效集合均返回 200，不重复插关联。文章保存及标签替换属于版本化写入，即使内容或集合相同，成功仍递增一次；使用旧 version 重提返回 409。节点新增返回新节点（children=[]）；节点更新返回目标节点和实际完整子树，不能把空 children 当成“未加载”。字段时间由数据库生成后重新查询，不能返回客户端伪造时间。

数据库唯一键冲突（username、deptCode、roleCode、permissionCode、tagName）返回 409，遵守现有数据库排序规则；分类名没有全局唯一约束，不额外发明一个。各写 Service 将已知 DuplicateKeyException 转成安全的 BusinessException(CONFLICT)，不能让现有未知异常兜底把它变成 500。未知 SQL/系统错误仍为 500，不将所有数据访问错误一概当作冲突。并发导致的已知外键引用冲突返回 409，不泄露 SQL 或约束实现细节。

### 8.2 查询条件、排序和空结果

所有可选条件使用 AND，省略条件不筛选。keyword 去首尾空白后做字面包含，空串不筛选；`%`、`_` 和转义符 `!` 作为普通字符处理，例如绑定转义后的 LIKE 参数并声明 `ESCAPE '!'`，不接受用户自带 SQL 通配查询。查询 ID 格式正确但不存在时返回 200 空列表/空分页；详情或写入的目标/引用不存在才返回 404。

| 接口 | keyword 或特殊筛选 | 默认排序 |
| --- | --- | --- |
| 员工分页 | username 或 realName；departmentId 含本部门和全部后代；status省略为全部 | updatedAt DESC，id DESC |
| 角色分页 | roleCode 或 roleName，status省略为全部 | updatedAt DESC，id DESC |
| 权限分页 | permissionCode 或 permissionName，permissionType精确；状态/类型省略为全部 | updatedAt DESC，id DESC |
| 后台标签分页 | tagName，status省略为全部 | tagName ASC，id ASC |
| 后台文章分页 | title 或 summary，不搜索正文；分类含后代、标签/作者精确；状态省略为数据范围内全部 | updatedAt DESC，id DESC |
| 待审核分页 | title 或 summary；固定 PENDING_REVIEW，不接受 status，排除本人文章 | updatedAt ASC，id ASC |
| 门户文章分页 | title 或 summary；固定 PUBLISHED/ALL/未删除；分类含后代、标签精确 | publishedAt DESC，id DESC |
| 门户标签分页 | tagName，只含启用且有可读已发布文章的标签 | tagName ASC，id ASC |
| 审核历史分页 | 目标文章读取范围；保留全部轮次 | reviewedAt DESC，id DESC |
| 日志分页 | userId/result精确；operation去首尾空白后精确，空串不筛选 | createdAt DESC，id DESC |

部门/分类树各层按 sortOrder ASC、id ASC；按 status 筛选时保留必要祖先的真实状态，不将停用祖先伪装为启用。门户目录另按第 3.2 节的可见文章与停用祖先规则过滤。树为空返回[]，所有叶子 children=[]。

文章 tags、绑定接口 tagIds、User.roles、角色已分配权限列表均按关联 ID 升序；PermissionCodes 去重并按 Java 字符串自然序排列。管理关联返回停用项以供回显；当前有效角色/权限只能从 AuthorizationSnapshot 获取。没有关联返回[]，目标用户/角色不存在返回404。

日志 createdFrom 包含边界、createdTo 不含边界，允许单独提供一端；同时提供时必须起始<结束，否则400。业务时间按已约定的上海本地时间解释。后台过滤在权限范围内执行，不能通过换 authorId/userId 绕过权限。

### 8.3 失败分类与检查位置

受保护请求的身份校验在 MVC 参数绑定前完成，失败为401；MVC 解码、参数类型及 Validation 失败为400，可能先于 Controller 的权限 AOP。正常进入 Controller 时由 B 的权限 AOP 检查功能权限，失败为403；业务 Service 再检查资源存在（404）、数据范围（403）和状态/版本/可分配条件（409）。不能要求只有 Controller AOP 就在参数绑定前返回403。

门户文章不存在、未发布或已删除统一404，不泄露后台内容；自审为403。事务内按共享服务的固定调用顺序报告最先发现的业务错误，验收用例分别构造单一错误，避免对多个同时错误假定额外优先级。条件更新影响行数为0时重新区分不存在与版本/状态冲突，不能直接按成功返回。

批量和关联替换先检查整个请求的数量、重复及ID格式；批量重复以 articleId 判断，即使 version 不同也是400。批量按ID顺序执行，任一失败整体回滚，成功结果再还原请求顺序。HTTP状态和外层code一致，前端不通过匹配message字符串判断业务类别。
